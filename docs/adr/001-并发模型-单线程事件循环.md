# ADR-001 · M1/M2 的并发模型：单线程事件循环

- **状态**：已定（依据 `DESIGN.md` §1.1「单进程、单线程、非阻塞」与 §1.4 不做清单）
- **日期**：2026-10-13
- **相关**：`DESIGN.md` §1.1 / §1.4、`TASKS.md` T2.x、`warmups/pc`（pthread 热身）

## 背景

曾经的直觉是：「高并发必须多线程/多进程，不然撑不住；而且 warmups 里刚学了 pthread」。
但 epoll 的整个意义就是**单线程管理成千上万条未完成连接**：静态文件服务器 90% 时间在**等网络**，
等待不消耗 CPU。本机实测（2026-10-13）：

| 事实 | 值 | 含义 |
|---|---|---|
| vCPU | 6 | 单线程最多吃 1 个核 → 多 worker 的动机是**利用率**，不是"撑不住并发" |
| `ulimit -n` | 1048576 | 一条连接一个 fd，200 / 1 万连接对 fd 毫无压力 |
| 线程默认栈 | 8 MB | "1 连接 1 线程"里最贵的部分（+ 内核 task + 上下文切换） |
| `wrk -t4 -c200` | `-t` = **压测机**线程数 | 与你服务器开几个线程**无关** |

## 选项

| 选项 | 好处 | 代价 |
|---|---|---|
| **A 单线程 + epoll ET**（M1/M2 现行） | 概念最小；事件循环本身就是学习目标；M2 的对照干净 | 只用一个核；一个阻塞操作会拖死全服（M2 正是要修它） |
| B 多进程 + `SO_REUSEPORT`，每进程单线程 epoll | 吃满多核（nginx 模型）；隔离性好（一个 worker 崩不影响其他） | 连接不共享：keep-alive / 超时各自为政 |
| C 线程池 + 每线程 epoll | 共享内存；可把磁盘 IO 卸载到线程池 | 锁与竞态；会把"事件循环"的学习目标冲淡 |

## 决定

M1/M2 **选 A**。多核问题留到 M4 用数据回答：同一台机、同一份 `wrk -t4 -c200 -d30s`，
对比 A 与 B 的 QPS / P99 / CPU 利用率，结论回答"单核是否已成为瓶颈"。
`warmups/pc` 学的 pthread 在那里用（以及为了以后读得懂 nginx/redis/muduo 的并发代码）。

## 后果

- M1/M2 的 `src/` 里出现 `pthread*` 就是跑偏；`http.c` / `file.c` 不得含任何并发知识。
- 若 M4 决定上 B/C：先改本 ADR 状态为「已修订」，并同步 `DESIGN.md` §1.4 与 `TASKS.md`。
- 已知边界：**单核上限**必须写进 README（否则读者会以为这台服务器"只能这么快"）。
